批量巡检智能工单空间的待分析缺陷：拉新 → 认领 → 派 3 个 agent 并行分析 → 落库并评论 → 汇总。
单条的分析方法与评论格式**全部沿用 `/bug_analyze`**，本 skill 只管调度、去重和收口。

> 用法：`/bug_patrol [--limit 30] [--agents 3] [--dry-run] [--fix] [--no-notify]`
>
> 定时跑：`/loop 30m /bug_patrol`

## 硬上限（不得突破）

| 项 | 值 | 说明 |
|---|---|---|
| 每轮处理 | **≤ 30 条** | `--limit` 只能调小不能调大 |
| 并行 agent | **≤ 3 个** | `--agents` 同上 |
| 单轮墙钟 | ~30 分钟 | 与巡检间隔一致，跑不完的**释放回队列**，下轮再来 |

🔴 **`--fix` 默认关闭。** 单条分析时人在旁边看着，批量无人值守时自动改代码推分支风险不对等。
需要自动修复请显式加 `--fix`，届时仍受 `置信度 ≥ 90` 约束。

## 🔴 分析并行，修复串行（不可违反）

**worker 永远不碰 git 写操作。** `--fix` 由巡检主控在所有 worker 返回后**串行**执行。

原因：`code/wobackend` / `code/woclient` / `code/wowebui` 每个仓库**只有一个工作树**，
3 个 worker 共用。并发 `git checkout -b` 的后果：

- 后切的分支把前面 worker 的工作树状态覆盖掉，前者接着写就写到错的分支上
- 抢 `.git/index.lock`，报 `Unable to create index.lock: File exists`
- worker A 改到一半，worker B 切走，A 的改动落在 B 的分支里

所以流程必须是：

```
并行：worker 分析 + 落库 + 评论（全程 git 只读）
  ↓  全部返回后
串行：主控逐条 checkout -b → 改 → 跑测试 → 提交推送
  ↓
收尾：发群通报
```

worker 的职责到「**在结论里写清完整修改方案**」为止，改动由主控执行。
这样也顺带保证了每个修复都经过主控复核，不是 agent 自说自话就推上去。

> 若将来真需要并行修复，正解是给每个 worker 开独立工作树
> （`git worktree add ../wo-worker-N <base>`），而不是共用一个。代价是磁盘和清理成本，
> 当前 5 条/轮的量级不值得，**别为这个提前上复杂度**。

⚠️ 还有一层：worker 读代码必须用 `git show origin/<分支>:<文件>`，**不能看工作树** ——
工作树可能正停在别人的分支或某个 `fix/` 分支上，读到的不是目标分支的代码。

🔴 **`--dry-run` 只分析、不落库不评论不通报**，前几轮建议先这么跑，确认产出质量再放开。

**飞书群通报默认开**（`--no-notify` 关），由本 skill 收尾统一发，见第 5 步。

## 执行步骤

### 1. 回收 + 拉新 + 看水位

```bash
python niuma/fsbm/patrol.py reap        # 先回收上轮死掉的 worker 占住的认领
python niuma/fsbm/sync.py               # 增量拉飞书新缺陷入库
python niuma/fsbm/patrol.py stats       # 看队列水位
```

`reap` 必须在 `claim` 之前：worker 中途挂掉会把缺陷永久占住，不回收队列会越漏越多。

### 2. 认领

```bash
python niuma/fsbm/patrol.py claim --limit 30 --buckets 3
```

一个事务里 `SELECT … FOR UPDATE` 再 `UPDATE`，多 worker 并发也不会认到同一条。
认领后 `sys_status` 置 `analyzing`，输出已分好 3 桶的 JSON。

**认领口径**（`patrol.py` 里的 `ELIGIBLE`，改判定改那里，别在 skill 里另写一套）：

- `frozen = 0` —— 人工冻结的不碰
- `sys_status = 'pending'` —— 已 analyzing / commented / fixed / skipped 的不重复处理
- `claimed_at IS NULL` —— 没被别的 worker 占着
- **`fs_analysis` 里没有记录** —— 这条就是「分析评论过的不再处理」

排序：P0 优先，同优先级下越新越先。

### 3. 派 agent

按桶派 agent，**一次性并发发出**，不要串行等待。每个 agent 的任务是：
对分到的每条缺陷，**照 `.claude/commands/bug_analyze.md` 的步骤走一遍**（取单 → 下图看图 →
分流 → 查日志 → 对代码 → 出结论 → 落库 → 评论）。

给 agent 的指令里必须写明：

- 缺陷清单（`work_item_id` + 标题 + 优先级 + env）
- 强制先读 `.claude/commands/bug_analyze.md` 和 `niuma/fsbm/评论要求.md`，不要自创流程
- 映射约定读 `niuma/fsbm/版本分支映射.json`，不要照抄任何人给的对应关系
- **代码只读**，禁止 `checkout`（本轮不带 `--fix` 时无一例外）
- 🔴 **传 `--no-notify`**：worker 不许自己发群消息，通报由巡检收尾统一发，否则一轮 30 条刷屏
- 🔴 **明确禁止 git 写操作**：不许 `checkout` / `checkout -b` / `commit` / `push`，
  即使本轮带了 `--fix` 也不行——修复由主控串行做，见上方「分析并行，修复串行」
- 🔴 **读代码前先 `git -C code/<repo> fetch origin`，再一律用 `git show origin/<分支>:<文件>`**，
  不要读工作树。`origin/xxx` 是上次 fetch 的快照，不 fetch 就是在读过期代码——
  2026-09-17 有一条 P1 就这样：worker 读的是 fetch 前的 develop，给出了完整修复方案，
  而主控 fetch 之后发现问题当天已被别人修掉了，整条分析白做
- 🔴 **开工前重新拉一次飞书状态**：认领依据的是同步快照，认领到开工之间缺陷可能已被关闭。
  命中 `版本分支映射.json` 的「不分析状态」就立即
  `patrol.py release --work-item-id X --status skipped` 并跳过，不要分析、不要评论
- 处理完一条就落库一条，**不要攒到最后**——中途被打断已完成的不能丢
- 时间不够时，**剩下的调 `patrol.py release --work-item-id X --status pending` 放回队列**，
  不要硬撑，也不要草草给个低质量结论

### 4. 收口

每条缺陷必须有明确去向，不允许停在 `analyzing`：

| 结果 | `sys_status` | 动作 |
|---|---|---|
| 分析完成 | `commented` | 落 `fs_analysis` + 发评论 |
| 资料不全 | `skipped` | 落 `fs_analysis`（低置信度 + 写明缺什么）+ 发简短评论，见下 |
| 不属于本系统 | `skipped` | 落库说明理由，**不发评论** |
| 没跑完 | `pending` | `release` 放回，下轮再来 |

收尾再跑一次 `patrol.py stats`，`认领中` 应为 0。不为 0 说明有 agent 没收口，报出来。

### 5. 串行修复（仅 `--fix`，主控自己做，不派给 worker）

所有 worker 返回后，按置信度从高到低，**一条一条**执行：

```bash
git -C code/<repo> fetch origin
git -C code/<repo> checkout -b fix/bug_<ID> origin/<branch>
# 按 worker 给出的方案改 → 跑该仓库的测试与类型检查 → 提交 → 推送
```

- 只处理 `置信度 ≥ --min-confidence`（默认 90）的
- **一条做完（含推送、切回原分支或保持）再做下一条**，绝不并行
- 改完把 `fix_branch` / `commit_sha` 回写 `fs_analysis`（重跑 `save_analysis.py` 覆盖）
- 任何一条失败不影响其余，如实记录在汇总里

### 6. 通报飞书群（默认开，`--no-notify` 关）

```bash
python niuma/fsbm/notify.py --patrol-round <本轮已完成的 work_item_id，逗号分隔>
```

一条命令搞定：**P0 或置信度 ≥90 的逐条单独发**，最后**一条全量汇总**（汇总放最后，
群里最新一条就是本轮全貌）。阈值在 `notify.py` 的 `SOLO_WHEN` 一处。

只传**真正完成分析并落了库**的 id：

- 资料不足（置信度 < 30）的**不进通报** —— 群里刷「这条没法分析」没价值，飞书评论已经通知到人了
- 状态命中黑名单被跳过的、放回队列的，都不进通报
- 一条都没完成就**不发** —— 空跑一轮不必打扰群

## 资料不全怎么办（🔴 重点，别误导）

### 判定：满足任一即为资料不全

- 描述为空，或只有模板骨架（`【前置条件】【操作步骤】【预期结果】` 下面都是空的）
- 没有任何可定位的对象标识：工单号 / 订单号 / 店铺 / 顾客昵称 / 请求 id **一个都没有**
- 有截图但图里也没有可定位信息，且描述文字不足以复现
- 日志按所有能想到的关键词、放宽时间窗、两个环境都查过，**确实捞不到**事发记录

⚠️ **查不到日志本身不等于资料不全**——先换关键词、放宽时间窗、换 `--env` 再说。
时间窗要按事发日推，不是提单日。

### 评论怎么写

**只说三件事：缺什么、为什么没法继续、需要提单人补什么。**

🔴 **绝对不要**：猜根因、给「可能是…」的方向、列一堆无证据的排查建议、写「建议先复现看看」。
无证据的猜测会把人带偏，比不评论更糟。**宁可少说，不可误导。**

模板：

```
【AI分析】资料不足，暂无法定位，需要补充信息。

本条缺陷缺少以下信息，无法开展分析：
- <具体缺什么，逐条列，例如：未提供工单号或订单号，无法在服务端日志中定位到本次操作>
- <例如：描述中只有「页面报错」，没有报错文案与操作路径>

已尝试：<写清楚查了什么，例如：按店铺名 + 提单日前后 3 天在 test/prod 两套日志中检索，未找到匹配记录>

麻烦 @<负责人> 或提单人补充：<具体要什么，例如：出问题的工单号、事发大致时刻、报错截图>
补充后可重新分析。
```

落库时 `confidence` 给 **0-30**，`summary` 写「资料不足：缺 X」，`layer` 留空——
**没定位到就不要填责任端**，填了就是误导。

## 坑

1. **`reap` 忘在 `claim` 前面跑** → 死掉的 worker 永久占住缺陷，队列悄悄变小
2. **agent 攒到最后一次性落库** → 中途断了全丢
3. **资料不全却给了「可能的方向」** → 无证据的猜测把人带偏，这是本 skill 最容易犯的错
4. **30 分钟塞 30 条** → 单条真做完要好几分钟，实际跑不完很正常，放回队列即可，不要为凑数降质量
5. **跳过判定只看 `sys_status`** → 还要看 `fs_analysis` 有没有记录；发评论前再查一次飞书评论，
   防止库和飞书不同步导致重复刷屏
6. **给 agent 抄一份映射关系** → 必须让它自己读 `版本分支映射.json`，抄过去就固化了
7. **无人值守时自动改代码** → `--fix` 不给就绝不动代码
8. **同一条反复分析** → 落库后 `sys_status` 必须推进，停在 `analyzing` 会被下轮 `reap` 捞回来重做
9. **跳过第 1 步的 `sync`** → 拿旧快照认领，会认到已经关闭的单子。2026-09-02 就这么空跑了一条 P0
10. **只靠 `sync` 防过期状态** → 认领到开工之间仍有窗口，worker 开工前必须自己再拉一次状态
11. **worker 各自发群消息** → 一轮 30 条刷屏，通报只能由收尾统一发
12. **把资料不足的也推群** → 群里刷「没法分析」没价值，只落库 + 评论即可
13. **让 worker 并发执行 `--fix`** → 三个仓库各只有一个工作树，并发 `checkout -b` 会互相覆盖、
    抢 `.git/index.lock`，改动串到别人的分支上。2026-09-02 派单时发现，**修复必须串行由主控做**
14. **worker 读工作树里的代码** → 工作树可能停在别人的分支或某个 `fix/` 分支上，
    必须 `git show origin/<分支>:<文件>`
15. **读 `origin/<分支>` 前没 fetch** → 读到的是上次 fetch 的快照。缺陷提单当天往往正好
    有人在修，不 fetch 就会对着已经修好的代码写一份修复方案。2026-09-17 一条 P1 如此
