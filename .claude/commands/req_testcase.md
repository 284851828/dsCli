评审通过后，按定稿的需求生成**自测用例**。后面 AI 自测（步骤 10）和开发冒烟（步骤 11）都用这一份。

> 用法：`/req_testcase <需求单URL 或 id> [--decide]`

| 参数 | 默认 | 作用 |
|---|---|---|
| （无） | — | 只出文档，不推进阶段 |
| `--decide` | 关 | 落库并推进到「AI 需求分析与系统设计」 |

---

## 步骤

### 1. 确认阶段

```bash
python niuma/fsprm/stage.py show --id <id>
```

`stage` 必须是 `ai_testcase`。不是就停下并说明当前在哪。

### 2. 读定稿的需求

- `docs/req/req_<id>/prd/<最新日期>/prd.md` 与 `img/`
- `docs/req/req_<id>/01-AI分析_r<最后一轮>.md` 的问题清单 + `04-产品回复_r*.md`
  —— **产品的回复是需求的一部分**，很多验收细节只在回复里，不在 PRD 里
- 相关模块的现有行为：`docs/knowledge/索引.md`，以及 `git -C code/<repo> show origin/<分支>:<文件>`

### 3. 写用例

写到 `docs/req/req_<id>/05-自测用例.md`：

```markdown
# <需求标题> —— 自测用例

> 需求单：<URL>　依据：PRD <日期快照> + 01-AI分析_r<N> + 04-产品回复_r<N>
> 生成时间：<YYYY-MM-DD>

## 用例总览

| # | 场景 | 类型 | 端 | 能否自动验证 |
|---|---|---|---|---|
| 1 | … | 正常流 / 边界 / 异常 / 回归 | 服务端/管理后台/客户端 | ✅ / ❌ 需人工 |

## 详细用例

### TC-01 <一句话场景>

- **前置**：<数据、账号、配置>
- **步骤**：1. … 2. …
- **预期**：<可判定的具体结果，不是「正常显示」>
- **依据**：PRD 第 X 节 / 产品回复第 N 条
- **自动验证**：<具体怎么验：接口返回断言 / SQL 查询 / 页面元素；不能自动就写「需人工，原因：…」>
```

### 4. 覆盖要求

必须各有至少一条，缺哪类就说明为什么没有：

| 类型 | 要点 |
|---|---|
| 正常流 | 需求描述的主路径 |
| 边界 | 空值、极长、极大量、首末条、并发 |
| 异常 | 参数非法、依赖不可用、权限不足、重复提交 |
| **回归** | 本需求改动会波及的**既有**功能 —— 最容易漏，也最容易出线上问题 |

🔴 **每条用例的「预期」必须可判定**。「显示正常」「功能可用」这类不算预期，
到了自测阶段没人知道该断言什么，等于没写。

🔴 **老实标注不能自动验证的**。依赖真实支付、短信、第三方回调、人眼判断视觉效果的，
就写「需人工」并写明原因。硬说能自动验证，到步骤 10 会造出假的自测报告。

### 5. 落库并推进（仅 `--decide`）

```bash
python niuma/fsprm/stage.py item --id <id> --kind artifact \
  --title "自测用例" --path "docs/req/req_<id>/05-自测用例.md" --author "<model>" --commit

python niuma/fsprm/stage.py decide --id <id> --verdict pass --actor "<model>" \
  --reason "生成 N 条用例，其中 M 条需人工验证"
```

### 6. 转述

告诉用户：总用例数、四类各几条、**需人工验证的有哪几条**（这几条决定了后面自测能自动到什么程度）。
