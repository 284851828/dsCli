# dsCli 测试规范

> 版本 v1.0（2026-11-09）。本文是 dsCli 与自动化开发平台、CI 之间的**协议**。
> 平台只依赖本文写明的命令、环境变量、输出格式、退出码和文件位置，不依赖 dsCli 的内部实现；dsCli 也不依赖任何平台的内部实现。
> 第一个使用方是 xCode，本文同时满足 xCode《老项目自动化测试标准》v1.0。机器可读的配置见根目录 `xcode.yaml` / `xcode.json`，操作步骤见 [自测说明](自测说明.md)。

## 1. 测试分层

| 层 | 测什么 | 位置 | 框架 | 进全量测试 | 需要网络、密钥 |
|---|---|---|---|---|---|
| **protocol** | 本文第 4 节的输出协议没有被破坏 | `tests/protocol/` | node:test | 是 | 否 |
| **unit** | dsCli 自己代码的单元测试 | `code/packages/claude-compat/**/tests/`、`code/packages/bundle/dscli/tests/`、`code/**/*dscli*.spec.ts` | vitest | 是 | 否 |
| **acceptance** | 黑盒验收：从命令行入口驱动 dsCli，检查参数、stdin/stdout/stderr、退出码、会话文件 | `tests/acceptance/` | node:test + `tests/lib/harness.mjs` | 是 | 否（用本机模型桩） |
| **e2e** | 接真实模型跑通主流程 | `tests/e2e/` | node:test | **否**，手动或定时跑 | 要 `DEEPSEEK_API_KEY` |

- **上游 DSH 自己的测试不在这里跑**。`code/` 是上游的副本（见 `code/UPSTREAM.md`），上游测试有上万条，由上游维护。dsCli 改了上游文件时，要在 unit 层补一个 `*dscli*.spec.ts` 覆盖改动。
- e2e 结果受模型影响，不稳定，还会产生费用，所以不放进平台每次都跑的全量测试。

## 2. 目录约定

```text
xcode.json                 平台读取的测试命令（受保护）
xcode.yaml                 xCode 标准格式的完整配置（受保护）
tests/
  run.mjs                  统一测试入口（第 3 节）
  lib/harness.mjs          验收测试公共工具：启动 dsCli、模型桩、临时工作区
  lib/reporter.mjs         输出协议的实现（第 4 节）
  protocol/fixture.mjs     协议自检样例，不以 .test.mjs 结尾，不会被当成测试收集
  acceptance/*.test.mjs    需求 #14（0.01）的验收测试，历史原因平铺在根下，不要移动
  acceptance/req_<需求编号>/*.test.mjs   之后每个需求的验收测试放在自己的目录
  e2e/**/*.test.mjs        真实模型测试
docs/测试规范.md、docs/自测说明.md
```

**为什么每个需求一个目录**：用例编号（TC-01、TC-02…）是按需求编的，不同需求会重复。放在各自目录下，用例名前面自动带上目录（第 4.2 节），名字就不会冲突；某个需求的新功能测试命令也能只跑自己的目录。

## 3. 命令（协议接口）

所有命令都在**仓库根目录**执行，只用相对路径；Windows 下用 cmd 调用。

| 用途 | 命令 |
|---|---|
| 一次性准备（新副本第一次使用前） | `pnpm -C code install --frozen-lockfile`，然后 `pnpm -C code run build` |
| **全量测试**（平台的项目测试命令） | `node tests\run.mjs`，等于 protocol + unit + acceptance |
| **某个需求的新功能测试** | `node tests\run.mjs acceptance --only req_<需求编号>` |
| 只跑某一层 | `node tests\run.mjs unit`（或 `protocol`、`acceptance`、`e2e`），可以写多个 |
| 按用例名筛选 | 加 `--grep "<正则>"`，如 `--grep "TC-0[1-5]"` |

**退出码**：`0` 全部通过；`1` 有失败、有跳过或运行出错；`2` 参数用法错误。

**写新功能测试命令时的规则**（平台让测试 AI 写这条命令时，按这里写）：

- 只写一行：`node tests\run.mjs acceptance --only req_<需求编号>`。
- **不要 `cd /d <绝对路径>`**：平台可能在别的副本目录里执行（多需求并行），写死路径会跑到别人的代码上。平台保证当前目录就是仓库根目录。
- 不要读取真实密钥，不要依赖个人机器上的路径。

## 4. 输出协议

平台从测试输出里识别**每个失败用例的名字**，用来区分「开发前就失败的」和「这次新增的失败」。所以输出格式是协议的核心。

### 4.1 结果行

protocol、acceptance、e2e 三层由 `tests/lib/reporter.mjs` 输出，**每个用例一行**：

```text
✓ acceptance/req_15/stream > TC-03 [P0] 标题 (12ms)
✕ acceptance/req_15/stream > TC-04 [P0] 标题 (35ms)
  │ AssertionError [ERR_ASSERTION]: 退出码应为 0
  │     at ...
✕ acceptance/req_15/stream > TC-05 [P1] 标题 (0ms)
  │ 跳过：规范不允许跳过（原因）

ℹ 用例 44　通过 42　失败 2　跳过 0
失败用例：
  - acceptance/req_15/stream > TC-04 [P0] 标题
```

| 规则 | 说明 |
|---|---|
| `✓`（U+2713）开头 | 通过 |
| `✕`（U+2715）开头 | 失败。这是 jest / vitest 的惯用写法，常见平台都认识。**不用 node 自带的 `✖`**，很多平台不认 |
| `│` 开头的缩进行 | 失败原因、测试自己打印的日志。**一律加这个前缀**，测试日志里即使出现 `✕ xxx` 也不会被误认成结果行 |
| 末尾的 `(12ms)` | 耗时，识别用例名时去掉 |
| 跳过 | **算失败**，输出 `✕` 行，原因写在下一行。规范不允许跳过（见 5.3） |
| `ℹ` 汇总行和「失败用例」清单 | 给人看，平台不依赖 |

unit 层用 vitest **默认输出**，失败行是 `FAIL  <文件> > <用例>` 和 `×`，本身就是常见格式，不再转换。

### 4.2 用例名

用例名 = `<测试文件相对 tests/ 的路径，去掉 .test.mjs>` + ` > ` + 各层父用例名 + ` > ` + 用例标题。

- 例：`tests/acceptance/req_15/stream.test.mjs` 里的 `test('TC-03 [P0] 标题')` → `acceptance/req_15/stream > TC-03 [P0] 标题`。
- 子用例失败时只输出子用例那一行，父用例不重复输出。
- 名字必须**稳定、唯一**：同一个用例每次跑名字都一样，不能放时间戳、随机数、临时路径。

### 4.3 自检

`node tests\run.mjs protocol` 用一个故意含失败、子用例、跳过和伪造日志的样例（`tests/protocol/fixture.mjs`），检查上面的规则。全量测试会先跑它，**协议被破坏时全量测试直接失败**。修改 `reporter.mjs` 后必须通过这一层。

## 5. 编写测试

### 5.1 用例命名

```js
test('TC-03 [P0] -p + 位置参数，默认 text 输出最终回复并退出 0', async (t) => { ... })
```

- 格式 `TC-<两位编号> [P0|P1|P2] <标题>`，编号和 `03-测试用例.md` 里的一致。
- 同一个文件里编号唯一。不同需求靠目录区分，不用全局唯一。
- **P0、P1 必须自动化并全部通过**；P2 可以只写在用例文档里。

### 5.2 验收测试只做黑盒

- 只通过这些接口驱动产品：`code\bin\dsCli.cmd`、`node code/apps/cli/lib/bin.js --profile dscli`、`--dump-config` 的输出、进程退出码、stdout/stderr、`$DSH_HOME/sessions` 下的会话文件。
- **不 import 产品源码**。需要的工具都在 `tests/lib/harness.mjs` 里：`runCli`、`makeWorkspace`、`startStub`、`jsonLines`、`findSessionFiles` 等。
- 模型一律用 `startStub()` 起的本机模型桩，**不连真实模型、不联网**。真实模型只在 e2e 层。

### 5.3 稳定性要求

| 要求 | 做法 |
|---|---|
| 不跳过 | 不写 `skip`、`todo`。条件不满足就让用例失败并说明原因。暂时修不了的列进 `xcode.yaml` 的 `known_failures` |
| 互不依赖 | 每个用例自己建工作区（`makeWorkspace`），不依赖其他用例的执行结果和顺序 |
| 可重复 | 跑两遍结果一样；用例结束清理自己的临时目录 |
| 有超时 | 子进程用 harness 的默认超时（120 秒），需要更长的显式写出来 |
| 输出不截断 | 用默认输出，不要自己吞掉断言信息 |

### 5.4 谁可以改测试

| 角色 | 可以 | 不可以 |
|---|---|---|
| 测试 AI（或写验收测试的人） | 新增、修改本需求目录下的验收测试 | 改其他需求的测试 |
| 开发 AI（或写实现的人） | **新增**单元测试文件 | 修改、删除已有的任何测试，修改 `tests/lib/`、`xcode.json`、`xcode.yaml` |
| 维护者 | 修改 `tests/lib/`、`tests/run.mjs` 和本文 | — |

开发中认为某条验收测试写错了，写进需求目录的 `用例质疑.md`，交给平台裁决，不要直接改测试。

## 6. 隔离（沙箱）

dsCli 没有数据库、缓存和常驻服务。隔离都在**每个用例内部**完成，不需要单独起停沙箱：

| 要求 | 实现 |
|---|---|
| 独立的数据目录 | `makeWorkspace()` 给每个用例建临时目录，`DSH_HOME`、会话、配置都在里面；目录名包含 `XCODE_SANDBOX`，并行的副本不会共用 |
| 外部依赖用 mock | 模型由 `startStub()` 提供，监听 `127.0.0.1` 的随机端口，并行不冲突 |
| 绝不连接生产 | `cliEnv()` 会清掉继承来的 `DEEPSEEK_*`、`ANTHROPIC_*`、`DSCLI_*`、`DSH_*`、`CLAUDE_CODE_*` 变量，只注入指向模型桩的地址和假密钥 `test` |
| 不留残留 | 子进程超时后结束整棵进程树；临时目录在用例结束时删除 |

所以 `xcode.yaml` 的 `sandbox` 写成空操作。

## 7. 环境变量

**平台提供**（dsCli 只读取，不要求必须有）：

| 变量 | 用途 |
|---|---|
| `XCODE_SANDBOX` | 并行实例名，用在临时目录名里；没有时用 `local` |
| `XCODE_SLOT`、`XCODE_WORKDIR`、`XCODE_MAIN_DIR`、`XCODE_REQ` | 目前不使用 |
| `CI=1` | 关闭交互 |

**项目需要**：

| 变量 | 用途 | 哪一层用 |
|---|---|---|
| `DEEPSEEK_API_KEY`（可选 `DEEPSEEK_BASE_URL`） | 真实模型密钥 | 只有 e2e；缺少时 e2e **直接失败**，不跳过 |

密钥只放在本机环境变量或被 git 忽略的 `info.txt` 里，不写进任何提交的文件。

## 8. 受保护的测试文件

平台应保护下列文件，开发阶段的改动会被恢复。对应 `xcode.yaml` 的 `test_globs`，**在 xCode 里登记项目时，「测试文件范围」填这几行**：

```text
tests/**
xcode.json
xcode.yaml
code/packages/claude-compat/**/tests/**
code/packages/bundle/dscli/tests/**
code/**/*dscli*.spec.ts
```

不要用「所有 `*.spec.ts`」：那会把上游 DSH 的上万个测试文件也纳入保护，改上游代码时就没法同步更新上游自己的测试。

## 9. 一个新需求的测试流程

1. **写用例**：`03-测试用例.md` 里按 P0/P1/P2 列出用例，编号 TC-01 起。
2. **写验收测试**（测试 AI）：在 `tests/acceptance/req_<需求编号>/` 下新建一个或几个 `*.test.mjs`，`import` 用 `../../lib/harness.mjs`，用例名按 5.1 节。
3. **定新功能测试命令**：`node tests\run.mjs acceptance --only req_<需求编号>`。
4. **开发**（开发 AI）：只改实现，可以新增单元测试。自测时跑第 3 步的命令，最后跑一次全量。
5. **验收**：平台跑新功能测试命令和全量测试 `node tests\run.mjs`，按第 4 节识别失败用例，和开发前对比不能有新增失败。

## 10. 修改本规范

本文、`tests/run.mjs`、`tests/lib/reporter.mjs` 一起构成协议。改协议时：

- 先改本文，再改代码，`node tests\run.mjs protocol` 必须通过；
- 版本号加一，在下面记一笔；
- 输出格式（第 4 节）的改动要先和使用方（xCode 等）确认，对方的识别规则要同步更新。
